# aika static timing dashboard

The dashboard is deliberately two static files:

- `index.html` contains all CSS and JavaScript and has no CDN dependencies.
- `data.json` is regenerated by `tools/clock-dashboard` from the existing `gpsstat`
  command. It contains seven days at the five-minute collection resolution, 15-minute
  samples through 30 days, and hourly samples through one year. The private JSON-lines
  archive keeps every five-minute collection for the full year.

At the 2026-09-13 baseline the private archive averaged about 1.77 kB per sample. A
year at five-minute resolution is therefore about 186 MB, against 4.1 GB free on
`/dev/root` at the time the policy was enabled. A synthetic year built from live sample
shapes produced a 5.4 MiB tiered public file. Disk usage should be rechecked if samples
gain large new fields or available root space drops substantially. Republishing that
whole file every five minutes would transfer about 1.5 GiB/day; split archives or
conditional publication should be added if that becomes material to the host.

Normal collection appends one durable JSONL record. Once records begin passing the
one-year cutoff, the collector rewrites the archive at most daily to remove them; it
does not rewrite the eventual 186 MB file every five minutes. Public output is filtered
to exactly one year even during the private archive's one-day pruning slack.

The page offers live windows from 30 minutes through one year. Its custom `from` and
`to` inputs use the browser's local time; applying them creates fixed ISO timestamps in
the URL so the view can be bookmarked or shared. Selecting any preset returns to a
window ending at the current time, and `latest 24h` resets the custom form directly.

The collector does not read Chrony's log directory. `gpsstat` is the canonical view of
this particular rig because it checks the whole path—Chrony, gpsd SHM, the GNSS fix,
receiver accuracy, and the PPS hardware—instead of assuming that a tracking log means
the receiver is healthy. It also archives the ZED-F9T `UBX-MON-RF` jamming state/raw
indicator for each RF block and the `UBX-NAV-STATUS` spoof-detection state.

## Installed layout on aika

The live installation is:

- collector: `/home/mui/bin/clock-dashboard`
- private full history: `/home/mui/.local/state/clock-dashboard/history.jsonl`
- publication staging: `/home/mui/clock-dashboard`
- schedule: `/etc/cron.d/aika-clock-dashboard`
- SFTP publisher: `/home/mui/bin/publish-clock-dashboard`
- public destination: `user7983935@ftp.kuvat.fi:/public_html/clock`
- public URL: <https://www.mui.fi/clock/>

For a local preview, run `python3 -m http.server 8000 --directory
"$HOME/clock-dashboard"` and open port 8000. Opening `index.html` directly as a
`file:` URL will not work in all browsers because the page fetches `data.json`.

## Cron and publishing

The installed cron file runs the collector and then publishes both files every five
minutes. It takes roughly 15 seconds because `gpsstat` waits for live gpsd and receiver
samples.

```cron
SHELL=/bin/sh
PATH=/home/mui/bin:/usr/local/bin:/usr/bin:/bin
*/5 * * * * mui /home/mui/bin/clock-dashboard --gpsstat /home/mui/bin/gpsstat --history /home/mui/.local/state/clock-dashboard/history.jsonl --output /home/mui/clock-dashboard/data.json >>/home/mui/.local/state/clock-dashboard/cron.log 2>&1 && /home/mui/bin/publish-clock-dashboard >>/home/mui/.local/state/clock-dashboard/cron.log 2>&1
```

The ignored `.ftpauth` file contains the raw SFTP password and is installed at
`/home/mui/.ftpauth` with mode `0600`. `clock-dashboard-askpass` supplies it without
placing the password in command arguments or logs. `dashboard/sftp.batch` uploads each
file under a temporary name and renames it, preventing browsers from observing a
partial transfer. The public copies are mode `0644`.

The old `/var/log/ntpstats` directory is not required. Chrony can write tracking and
statistics logs when configured to do so, but those files cover only the clock servo.
The collector keeps its own compact JSON-lines history and includes the GNSS and
hardware checks that make `gpsstat` useful.

## Meaning of the headline numbers

`PPS short-term scatter` is Chrony's standard deviation for `PPS2`. `Receiver
estimate` is ZED-F9T `NAV-TIMEGPS.tAcc`. `Max-error bound` is root dispersion plus
half root delay, as calculated by `gpsstat`.

None of those is a measurement of constant absolute bias. Chrony compares the system
clock with PPS and then steers that clock to PPS, so fixed antenna, receiver, cable,
and timestamping delays disappear into the correction. The dashboard says this
explicitly. Once the PPP clock solution is available, a separately calibrated UTC-bias
field can be added without relabelling servo offset as absolute accuracy.

The RF panel is likewise an indicator, not an authentication system. `jamInd` is the
receiver's continuous-wave interference metric on a 0–255 scale and its jamming state
is the receiver's own classification. The spoof state reports what the receiver
detector indicated; “none indicated” is not proof that every received signal is
authentic. The history is useful for correlating changes with C/N0, satellite count,
position, and timing behavior.

`gpsstat` does not take the receiver's jamming state at face value. At this site RF
block 0 reads a steady indicator of about 60 and a permanent WARNING, so it is judged
against a per-block baseline (`F9T_RF_BASELINE`, default `0:60 1:7`, tolerance
`F9T_RF_TOLERANCE=15`): within it is a NOTE, a departure in either direction is a WARN,
and CRITICAL is still a FAIL. The panel above still shows the receiver's raw state. The
stronger spoofing check is the rubidium: with PPS2 selected, `gpsstat` warns when
chrony's live clock frequency is more than 2e-8 from GNSS or the PPS2 offset exceeds
1 µs, since the AR-40A cannot be moved by a spoofer. The live frequency is archived as
`ref_freq_live`.

The MIKES comparison plots Chrony's adjusted offset for each of the three configured
national time-service servers. Positive means the local clock is ahead of the server;
the displayed `±` value is the NTP root distance. Network delay and sample noise make
this a useful millisecond-scale sanity check, not a calibration of the GNSS PPS or its
fixed delays.
